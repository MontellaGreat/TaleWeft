# preview.7 功能落实与 Anti-AI 对抗审计

审查日期：2026-10-24。对象：当前 `PlotPilot-4.6.0` 源码、运行中的网页版数据只读快照，以及 `TaleWeft-0.1.0-preview.7-x64-setup.exe` 解包后的后端。

## 结论

**功能确有实际实现，但还不能算完整验收。** 新书 DAG、偏离模型审阅、本地 Anti-AI 扫描、按报告修复、提交门禁、章节编辑后的后台重算，均能追到实际执行代码和持久化结果。与此同时，独立反例确认了 7 类缺陷；人物审核锁及保存回读组合存在高优先级漏洞。还有零规则覆盖、编辑后计划快照保留等边界，需要明确处理。

**当前 Anti-AI 的准确含义是：对选出的文本执行当前版本的本地规则扫描，命中后可调用模型改写，再重新审核。** 当前网页快照启用了 51 条规则。它不等同于全面的模型语义文风审稿，也不等同于“识别是否 AI 写作”。“零命中”只能证明选中的文本未命中这些规则，不能证明没有 AI 味。

此前“回归测试通过”的结论，对当时列出的测试成立；将其扩大为“所有功能均完整可靠”则没有足够依据。本轮独立复现说明，旧用例遗漏了若干真实路径。

本轮只新增审计脚本、隔离测试与报告，**没有修复下述生产缺陷，没有重打安装包**。这些问题仍存在于已交付的 preview.7 中。

## 审查方法与证据等级

复用项目现有开源实现，沿“界面入口 → API → 服务 → 执行器 → 数据库 → 回读”核对，由三路子 agent 分别检查 Anti-AI、新书 DAG、模型与手动改章，再由主审独立复跑关键反例。

- **实际运行证据**：从当前网页数据库以 SQLite `mode=ro` 建立隔离快照，核对已完成的世界观运行；在隔离副本调用真实扫描器复扫。没有占用用户正在运行的任务或更改其书目。
- **独立反例**：使用真实服务、API handler、SQLite 和扫描器；仅远程模型响应使用可控替身。用于证明程序路径，不冒称真实模型质量验收。
- **网络证据**：国内模型下载源使用生产探测器，读取元数据、配置和权重响应的 1 字节；没有下载整个模型。
- **产物证据**：对解包安装器中的 PYZ 生产模块与当前源码编译结果比较，不执行模块正文。

本轮没有新增付费模型请求，也没有重跑完整桌面安装/卸载、完整下载与全书真实生成。市场分类完整性、全部旧编辑器功能及所有自定义 DAG 组合不在本轮全面验收范围内。

## 确认缺陷及修复验收条件

### F01 · P1：人物写入口绕过审核锁，未审核字段还能获得 verified

位置：`interfaces/api/v1/workbench/sandbox.py:134`、`interfaces/api/v1/engine/checkpoint_routes.py:737`、`application/onboarding/setup_generation.py:198` 和 `:1034`。

锚点 PATCH 及人物 extract/auto-fill 没有调用审核锁。人物回读仅比较姓名、性别、年龄、外貌、性格、核心信念、核心动机，遗漏 description、background、voice、mental_state、verbal_tic 等字段。

**独立复现**：在审核未完成的临时书目中，正常锁检查会拒绝编辑，但两个现有 API handler 仍成功写库。再在审核提交后、回读前，通过锚点 PATCH 将 verbal_tic 改成未经审核的值，真实 `commit()` 和 `_verify_unit()` 仍返回 `saved_data_verified=True`，并把新值纳入 approved。没有篡改审核哈希或替换提交实现。

**影响**：绿色完成状态不一定代表数据库中的全部人物资料就是审核过的版本。这是本轮优先修复项。

**修复与验收**：统一共享写服务的审核锁和运行归属检查，覆盖所有写入口；完整规范化比较全部已审核持久化字段。并发修改必须被拒绝，或令审核失效并中止提交，不能静默吸收未审核值。验收要覆盖 API 旁路及“提交 → 回读”并发窗口。

### F02 · P2：按全局字段名跳过文本，漏扫最后保存的内容

位置：`application/onboarding/setup_generation.py:210`、`:234`；`application/world/services/bible_setup_continuation.py:242`。

`role/label/target/name` 等被全局当作非正文字段。例：人物 role 为“眼中闪过一丝笑意的主角”，description 为正常介绍，向导扫描通过；保存时 role 又被拼入正式 description，同一真实扫描器扫描合成后的文本会命中 **2 条**。嵌套 `voice_profile.label` 同样可能漏扫。

**修复与验收**：按具体 schema/path 定义标识符与叙述字段，审核最终规范化保存表示；必须保证“被审核的文本”和“正式保存的文本”一致。用真实扫描器覆盖 role 拼接、嵌套语气标签和正常人名保留，不能把 scanner 替换为固定通过。

### F03 · P2：文风规范引用禁词，被当成故事正文违规

位置：`application/onboarding/setup_generation.py:879`、`:902`、`:923`。

输入正确规范：“禁止使用‘嘴角上扬’‘眼中闪过一丝’等套话，用人物的动作与对白推进情节。”真实扫描会判不通过。系统无法区分规范里引用的反例与正文实际使用，可能无意义改写禁用规则，或反复修复后阻止保存。

**修复与验收**：区分规范审阅和故事正文扫描，结构化保留禁用表达，不能靠删除所有引号内容粗略放行。同样套话放在“禁止规则”应保留，放在叙述正文仍应被发现；嵌入指令或借引用藏正文也要有反例。

### F04 · P2：尾段专项能力没有联通；终章注入缺少运行标记

位置：`application/engine/rules/mid_generation_refresh.py:138`、`:148`；`application/engine/dag/nodes/anti_ai_nodes.py:366`、`:375`；`application/engine/dag/runtime.py:211`。

仓库定义了尾段专项检测器，但未发现生产调用者。六个专项样本（如“一切才刚刚开始。”“他知道自己再也回不去了。”）在通用真实扫描中全部零命中，专用检测器能指出对应问题。

`anti_ai_finale` 自身定义为**生成前提示词注入**，返回 finale_block，不是生成后正文审查；这类注入有实际用途，不能按“未调用模型”判成无用。但其依赖的 `is_final_chapter` 在标准 runtime 初始化中没有设置；输入章节号和目标章数都为 10，注册执行器仍 bypass。即使手工置真，它也只返回提示词片段，不能代替尾段检查。

**修复与验收**：从权威章节计划传递终章状态，并允许作者确认；将需要的尾段专项检测接入生成后审核/修复复验。界面区分“提示词已注入”“正文已扫描”“修复已完成”，正常非终章 bypass 则保持真实展示。覆盖普通章、终章、续作/改目标章数等场景。

### F05 · P2：七个世界观单元忽略原 CPMS 自定义提示词正文

位置：`application/onboarding/setup_generation.py:574–596`。

读取了 setup_prompt_source，却对文风、五维和完整复审使用硬编码 system 与 schema，最终 user 只包含基础设定、前置资料、当前单元契约。七个单元分别加入独有自定义 marker 后，最终生成提示词全部丢失 marker。

**影响**：作者在原提示词里添加的额外创作约束未送到模型。基础设定仍在，市场画像通过后续独立 hook 注入；两者并非全部丢失。

**修复与验收**：在分步输出约束下保留原自定义约束，将最终实际发送的组合提示词冻结展示。七个单元均需验证自定义 system/user 约束确实到达调用端；不能只检查数据库里曾保存过这段提示词。

### F06 · P2：模型就绪检查放过确定无法发送的参数组合

位置：`application/ai/model_readiness_service.py:43`；`application/ai/llm_control_service.py:488`、`:724`；实际拒绝点为 `infrastructure/ai/providers/anthropic_provider.py:245` 和 `infrastructure/ai/providers/openai_provider.py:400`。

两例均可保存、返回 ready=true，却在真实 Provider 发出 HTTP 之前被拒绝：

1. Anthropic：thinking_budget_tokens=1024、max_tokens=4096、top_p=0.8。
2. OpenAI 自动协议选择 Chat 时：5 项 stop_sequences。

这是离线即可发现的配置冲突，与无法预知网络、余额或远端权限不同。前端虽有部分提示，但没有完整阻止保存。

**修复与验收**：保存、连通测试、就绪检查和真实 Provider 请求构造复用同一离线约束校验；针对自动协议区分可确定与需协商的约束。用真实请求构造验证，不能只 mock readiness。反证已确认：已知输出上限小于 max_tokens 的配置会被正确拒绝，不列为缺陷。

### F07 · P2：修复候选的直接来源指针指向旧候选

位置：`application/onboarding/setup_generation.py:864`、`:775`。

`_repair` 丢弃真实 repair attempt ID，随后 `_install_candidate` 把 source_attempt_id 写成原候选 ID。独立复现“拒绝 → 修复 → 复审”后，来源确实指错。真实模型修复调用仍在 model_calls 中，内容哈希可核对，因此不能说修复没有执行或内容丢失。

**修复与验收**：显式传递实际 repair attempt ID；另设 previous_candidate_id 表达修复前版本，不混用直接来源和历史版本关系。覆盖多轮修复、文风规范化、失败恢复，能从最终候选直接追到实际生成它的调用。

## 条件性风险与部分实现

### B01：全部规则禁用，仍显示普通“通过”

隔离数据库禁用全部 51 条内置规则且不添加自定义规则后，有效规则数为 0，真实扫描仍 completed/0 hits，向导 passed=true。当前网页快照有效规则为 51，**没有证据表明用户这轮运行遇到了零覆盖**。

建议回执展示有效规则数量和扫描模式；零规则应明确为“未执行有效规则检查/覆盖为空”，不能与正常扫描通过同义。此项应加入修复清单，避免配置变更后形成无效审核。

### B02：正文改写后的 micro_beats 仍为原计划快照

位置：`application/world/services/chapter_narrative_sync.py:387`、`:2427–2432`；`domain/shared/narrative_plan_contract.py:278`。

独立复现：旧微观节拍“主角收到铜铃”，新正文及抽取摘要变为“从未见过铜铃，已离开故乡”；叙事同步返回 synced 后，旧节拍仍在。抽取器的返回白名单也不接收模型返回的新 micro_beats。

源码把它定义为写作计划快照，保留原计划可能有复盘用途，**不能据此认定记忆、人物或整个章后工作流没运行**；该复现也只针对叙事同步阶段，未冒称完整任务最终状态。问题在于不能把现有行为称为“所有关联项自动全部刷新”。计划合同读取路径仍可能读取该字段，应进一步验证版本与语义边界。

建议将“原写作计划”和“正文实际事件”分开存储及展示，计划绑定正文版本，冲突时标记过期。保留旧计划用于复盘可以成立，但不能静默当成当前正文事实。编辑后的重算状态也应在主编辑器显示，目前失败/重试主要藏在历史版本弹窗；每次编辑尚无独立 DAG 图展示。

### B03：扫描规则覆盖和真实模型质量尚未完整验收

规则能发现特定套话，但隐性解释腔、重复结构、情感标签堆叠、过度总结等未必有匹配规则。偏离模型也可能给出错误审阅。程序真实调用与语义判断可靠是两项不同验收要求。

建议建立人工标注语料，包含套话、正常表达、题材专名、引用禁词、规则躲避和剧情偏离，分别衡量漏报、误报及改写事实保持；若增加语义去味审稿，应作为明确的新审核层，保存问题、证据片段、改写前后差异和复审结果，不能只返回一个分数。

## 安装包与源码对应性

从实际解包安装器的 `plotpilot-backend.exe` 读取 PYZ，对 application/domain/infrastructure/interfaces/engine 中能定位源码的 **899 个生产模块**重新编译并比较 CPython code object，**0 项不一致**。安装包核验记录中的另 29 个关键源文件哈希也无差异。

这表明已发现的缺陷适用于这份已交付的 preview.7 后端，不是只存在于另一个开发副本。这个校验不等同于整机安装验证，也不覆盖所有第三方依赖的运行行为。前轮已做过的前端文件核验和冷启动偶发超时限制仍以 preview.7 发布说明为准。
